# Многоэтапная рекомендательная система для интернет-магазина

Проект рекомендательной системы на основе датасета **OTTO Recommender Systems Dataset** с пользовательскими сессиями интернет-магазина.

Цель проекта — построить многоэтапную рекомендательную систему, которая по истории действий пользователя в текущей сессии формирует список из 20 товаров, наиболее релевантных для его следующих действий.

Система состоит из двух основных этапов:

1. **Генерация кандидатов** — из большого каталога товаров отбирается небольшой набор потенциально релевантных товаров с помощью истории сессии, co-visitation и популярности.
2. **Ранжирование кандидатов** — `CatBoostRanker` присваивает кандидатам score и формирует итоговый топ-20.

Релевантность товара определяется будущим действием пользователя:

- `0` — товар не появился в будущей части сессии;
- `1` — click;
- `2` — cart;
- `3` — order.

Таким образом, более значимые с точки зрения бизнеса действия получают большую релевантность при обучении модели.




## Постановка задачи

Исходные данные содержат последовательности действий пользователей внутри сессий:

- `clicks` — просмотр товара;
- `carts` — добавление товара в корзину;
- `orders` — покупка товара.

Для моделирования реального сценария каждая сессия разделяется на две части:

- **history** — действия, доступные рекомендательной системе в момент построения рекомендаций;
- **future** — последующие действия пользователя, используемые для оценки качества.

Для каждой сессии необходимо сформировать список из **20 товаров**, которые с наибольшей вероятностью окажутся релевантными в future-части сессии.

Основные метрики качества:

- **Recall@20** — какую долю релевантных товаров удалось найти;
- **Precision@20** — какая доля рекомендаций оказалась релевантной;
- **NDCG@20** — насколько хорошо релевантные товары расположены в верхней части списка рекомендаций.




## Архитектура решения

Рекомендательная система построена как двухэтапный пайплайн:

**История сессии → Генерация кандидатов → Расчёт признаков → ML-ранжирование → топ-20 рекомендаций**

### 1. Генерация кандидатов

Ранжировать весь каталог товаров напрямую слишком дорого, поэтому сначала для каждой сессии формируется небольшой набор товаров-кандидатов.

Используются несколько источников кандидатов:

- товары из истории текущей сессии;
- товары, связанные с ними через co-visitation;
- популярные товары в качестве fallback.

Размер candidate pool ограничен **100 товарами на сессию**.

### 2. Построение признаков

Для каждой пары `(session, candidate)` рассчитываются признаки, описывающие поведение пользователя и свойства товара:

- количество `click`, `cart` и `order`;
- общее количество взаимодействий;
- давность последнего взаимодействия с товаром;
- временной интервал между взаимодействиями;
- `covisitation_score`;
- глобальные доли `click`, `cart` и `order` для товара.

Признаки рассчитываются только на информации, доступной до момента построения рекомендаций.

### 3. Ранжирование

Для ранжирования кандидатов используется `CatBoostRanker` с функцией потерь `YetiRank`.

Каждая пользовательская сессия рассматривается как отдельная группа объектов. Модель обучается располагать товары с большей будущей релевантностью выше остальных кандидатов.

После получения score кандидаты сортируются внутри каждой сессии, и пользователю возвращаются **топ-20 товаров**.





## Данные

Используется датасет **OTTO Recommender Systems Dataset**, содержащий анонимизированные пользовательские сессии интернет-магазина.

Каждое событие содержит:

- `session` — идентификатор сессии;
- `aid` — идентификатор товара;
- `ts` — время события;
- `type` — тип действия (`clicks`, `carts`, `orders`).

В исходном датасете содержатся сотни миллионов событий, поэтому разработка пайплайна сначала проводилась на ограниченной выборке, после чего отдельно был проведён эксперимент с увеличением объёма обучающих данных.

Сами исходные данные и промежуточные артефакты не хранятся в Git-репозитории.







## Эксперименты и результаты

### Baseline

Перед обучением модели были построены простые эвристические baseline-модели. Это позволяет оценивать дальнейшие улучшения относительно простого решения, а не только по абсолютному значению метрик.

В качестве базовых подходов использовались:

- рекомендации популярных товаров;
- рекомендации последних товаров из истории сессии;
- ранжирование кандидатов по `covisitation_score`.

### ML-ранжирование

Для финального ранжирования кандидатов используется `CatBoostRanker`.

Модель оценивает товары-кандидаты внутри каждой сессии и формирует топ-20 рекомендаций.

На валидационной выборке были получены следующие результаты:

| Target | Recall@20 | Precision@20 | NDCG@20 |
|---|---:|---:|---:|
| Click | 0.2342 | 0.0789 | 0.2398 |
| Cart | 0.2991 | 0.0344 | 0.2210 |
| Order | 0.4995 | 0.0592 | 0.4097 |

Наиболее высокий Recall@20 получен для `order`: модель находит около половины релевантных товаров среди топ-20 рекомендаций.

Метрики для разных типов событий рассчитываются только по сессиям, в которых соответствующее релевантное событие присутствует.









### Влияние размера обучающей выборки

Отдельно был проведён эксперимент, чтобы проверить, насколько увеличение количества обучающих данных улучшает качество ранжирования.

Одинаковая модель была обучена на двух объёмах данных и проверена на одной и той же валидационной выборке:

| Обучающая выборка | NDCG@20 | Время обучения |
|---|---:|---:|
| 10 000 сессий | 0.5995 | 22.9 сек. |
| 40 000 сессий | 0.6010 | 120.0 сек. |

Увеличение обучающей выборки в 4 раза повысило NDCG@20 примерно на `0.0015`, при этом время обучения выросло более чем в 5 раз.

В рамках текущей архитектуры дополнительный объём данных дал небольшое улучшение качества. Это указывает на то, что дальнейший рост качества стоит искать не только через увеличение выборки, но и через улучшение генерации кандидатов, признаков и самой схемы ранжирования.










## Анализ модели

### Важность признаков

После обучения модели была проанализирована важность используемых признаков.

Наибольший вклад в качество ранжирования показали:

1. `item_recency` — насколько недавно пользователь взаимодействовал с товаром;
2. `item_interaction_span` — временной интервал взаимодействий с товаром;
3. `covisitation_score` — сила связи товара с другими товарами из текущей сессии.

Остальные признаки, связанные с глобальной частотой кликов, добавлений в корзину и заказов, оказались значительно менее важными.

Это показывает, что для текущей модели особенно важен контекст конкретной пользовательской сессии: недавние действия пользователя дают больше информации для ранжирования, чем глобальная популярность товара.

Важно: значения feature importance для `CatBoostRanker` показывают относительное влияние признаков на работу модели и не должны интерпретироваться как прямые проценты вклада в итоговую рекомендацию.








### Анализ ошибок

Для анализа ошибок отдельно рассматривались сессии, содержащие будущие заказы (`order`).

Качество модели заметно различается между сессиями: для части сессий релевантные товары оказываются высоко в топ-20, тогда как для других модель полностью пропускает будущий заказ.

Одним из ограничений системы является этап генерации кандидатов. Ранжирующая модель может переставлять только те товары, которые уже попали в набор кандидатов. Если релевантный товар отсутствует среди кандидатов, модель ранжирования не сможет его восстановить независимо от своего качества.

Таким образом, итоговое качество рекомендательной системы определяется двумя последовательными этапами:

1. генерация кандидатов должна обеспечить высокий Recall и включить релевантные товары;
2. модель ранжирования должна правильно расположить найденные товары внутри топ-20.

Это делает качество генерация кандидатов одним из основных направлений дальнейшего улучшения системы.







## Ограничения

Текущая версия проекта является offline-прототипом рекомендательной системы и имеет несколько ограничений:

- эксперименты проводились на подвыборке исходного датасета из-за вычислительных ограничений;
- используется ограниченный набор признаков, построенных на истории взаимодействий;
- качество модели зависит от покрытия релевантных товаров на этапе генерации кандидатов;
- offline-метрики не гарантируют аналогичного улучшения пользовательских и бизнес-метрик в production;
- для окончательной проверки рекомендательной системы в реальном продукте потребовался бы online A/B-тест.

## Финальные выводы

В проекте реализован полный (оффлайн) пайплайн  многоэтапной рекомендательной системы:

**история сессии → генерация кандидатов → построение признаков → ML-ранжирование → топ-20 рекомендаций.**

Основные выводы:

- многоэтапная архитектура позволяет сначала сократить пространство поиска до небольшого candidate pool, а затем использовать более сложную модель ранжирования;

- качество финального ранжирования ограничено качеством генерации кандидатов: отсутствующий в candidate pool товар невозможно восстановить на следующем этапе;

- наиболее полезными для текущей модели оказались временные признаки и co-visitation;

- увеличение обучающей выборки с 10 000 до 40 000 сессий дало лишь небольшой прирост NDCG@20 при существенном увеличении времени обучения;

- дальнейшее улучшение системы целесообразно искать в более качественной генерации кандидатов, дополнительных session-based признаках и развитии модели ранжирования.

Проект демонстрирует не только обучение модели, но и полный цикл разработки рекомендательной системы: постановку задачи, оффлайн-валидацию, реализация baseline, генерация кандидатов, feature engineering, ранжирование, анализ ошибок и проверку масштабируемости.
